# 분석형 슬라이드 v0.1 — 결론은 위, 근거는 아래

> 핵심 사상: **헤드라인은 주장이고, 아래 표·도식은 그 주장의 증거다.** 증거가 받쳐주지 못하는 헤드라인은 고치거나 뺀다.

## 🚨 GATE 0 — 즉시 중단 체크

1. 4종 세트(Word KR/EN + PPTX KR/EN) 요청이다 → STOP. `generate-full-report`로 넘긴다.
2. 덱이 아닌 글(칼럼·보고서·메모) 검증 요청이다 → STOP. `quality-core`로 넘긴다.
3. 헤드라인을 주제명(「시장 현황」「기술 동향」)으로 쓰려 했다 → STOP. 결론 문장으로 다시 쓴다.
4. 기억 속 수치·날짜·사건을 원문 확인 없이 장에 올리려 했다 → STOP. `claims.json`에 등록·검증부터 한다.
5. 렌더링 이미지를 보지 않고 「완료」라고 하려 했다 → STOP. Phase 5를 수행한다. 텍스트 추출 검사는 화면 검수를 대신하지 않는다.
6. 기존 덱 수정인데 이미 확정된 장의 내용·레이아웃을 요청 없이 바꾸려 했다 → STOP. 요청 범위만 고친다.

## 🛑 GATE 1 — 필수 읽기

```
1. references/slide-style.md                    ← 헤드라인 문형, 화면 규격, 장 유형별 양식
2. ../quality-core/references/claims-ledger.md  ← 원장 스키마와 verified/estimate/removed 규칙
3. ../quality-core/references/style-rules.md    ← 사실↔해석 문형 분리
```

사용자 문체 프로파일(메모리의 writing-style 등)이 있으면 초안 전에 함께 읽는다. 본인 원본 덱 재현이 필요하면 `references/style-sources.md`의 링크(로컬에서 채움)를 열어 직접 렌더링해 확인한다.

## 적용 우선순위

현재 요청 > 고객 지정 템플릿 > 기존 덱에서 확정된 내용·레이아웃 > 본 스킬 기본값.
본 스킬은 편집·검증 기준이며 PPTX·Google Slides 제작 도구를 대신하지 않는다. 실제 제작은 환경에 맞는 도구(pptx 스킬, Google Slides 커넥터, HTML→PNG 렌더 등)로 하고 본 스킬의 규칙을 얹는다.

**산출 형식 기본값**: 슬라이드는 장별 PNG 이미지로 전달한다. 편집 가능한 PPTX·PDF는 사용자가 명시할 때만 만든다(예: 강의용 덱은 PPTX + 발표자 노트).

## 워크플로 (6 Phase)

### Phase 1 — 과제 확인
목적, 청중, 발표 시간·장수, 산출 형식, 템플릿, 사용할 원문, 제외 범위를 확인한다. 이미 주어진 정보는 다시 묻지 않는다. 비어 있는 핵심 정보만 한 번에 묻고(AskUserQuestion), 물을 수 없거나 답이 없으면 가정을 `mapping.md` 맨 위에 적고 진행한다.

### Phase 2 — 요구사항 → 장 매핑표
제작 전에 아래 표를 만든다. 주제명만 적힌 목차는 매핑으로 치지 않는다.

| 요구사항 | 장 번호 | 그 장의 결론(헤드라인 초안) | 받쳐줄 근거(표·도식·수치·사례) | 근거 원문 |
|---|---|---|---|---|

전개는 해석 프레임 → 정의 → 배경 → 변화 → 시사점이 기본이다. 청중과 과제에 맞게 합치거나 순서를 바꿀 수 있다.

### Phase 3 — 원장 개설과 원문 대조
모든 수치·사건·인용·고유명사 관계를 `claims.json`에 장 번호(`slide` 필드)와 함께 등록한다. 대조 항목은 주체, 행위, 숫자, 단위, 시점, 대상 범위, 조건 7가지다.

- 전망·목표를 실적이나 확정 사실로 바꾸지 않는다.
- 복합 주장은 구성 요소별로 근거를 확인한다. 일부만 맞으면 전체를 verified로 두지 않는다.
- 사실·해석·제안을 구별한다. 해석과 제안을 출처가 직접 말한 사실처럼 쓰지 않는다.
- 1차 출처(기관·기업 원문)를 우선한다. 원문 페이지가 열리지 않으면 그 원문을 직접 인용한 신뢰할 만한 2차 보도(Reuters, 업계지 등)로 확인하고 verified로 두되, `note`에 확인 경로를 적는다.
- 같은 기업 자료끼리 수치가 엇갈리면(고객 수 600k/620k/645k 등) 그 수치는 removed로 빼거나 가장 최근 1차 자료 하나로 시점을 밝혀 쓴다.
- 정의·프레임워크는 작성자 해석이면 원장에 넣지 않고, 외부 기관 정의(ITU·Gartner 등)를 인용할 때만 `quote`로 등록한다.
- 확인하지 못한 주장은 장에서 빼거나 결론 강도를 낮춘다. 「미확인」「확인 필요」 같은 표시를 산출물에 남기지 않는다. 꼭 필요한 자료를 열지 못했으면 사용자에게 그 자료를 요청한다.

### Phase 4 — 장 작성
- 각 장은 상단에 분석 결론 하나, 하단에 그 결론을 받치는 표·도식·비교·수치·사례를 둔다.
- 하단 근거가 상단 문장을 실제로 지지하는지 장마다 확인한다. 지지하지 못하면 헤드라인을 근거 수준으로 낮춘다.
- 헤드라인 문형, 표기, 장 유형별 양식은 `references/slide-style.md`를 따른다.
- 과밀한 표·긴 문단은 도식이나 여러 장으로 나눈다. 단, 출처와 조건이 사라질 만큼 단순화하지 않는다.

### Phase 5 — 렌더 검수
최종 산출물을 실제로 렌더링해 **모든 장의 이미지를 눈으로 본다.**

```
python3 references/render_slides.py deck.pptx out_dir/     # PPTX/PDF → 장별 PNG + contact_sheet.png
python3 references/render_slides.py html_dir/ out_dir/     # slide-*.html → PNG(Playwright) + contact sheet
python3 references/render_slides.py png_dir/ out_dir/      # 이미 만든 PNG → contact sheet만
```

점검 항목: 잘림, 겹침, 가독성(`slide-style.md` 1-1의 최소 글자 크기), 하단 빈 공간, 정렬, 색 대비, 표·도식과 헤드라인의 연결, 출처 표시.
오류를 고치면 영향받은 장을 다시 렌더링하고, 공통 요소(마스터·제목 위치·색)에 손댔으면 전 장을 다시 본다.

### Phase 6 — 수정 후 전파 점검과 전달
- 바뀐 문장·표·도식의 의미와 근거를 다시 확인한다.
- 한 장에서 오류 유형(수치 단위, 용어 불일치, 전망→실적 오기 등)을 찾으면 같은 유형을 전 장에서 찾는다.
- 최신 요청을 실제 산출물과 한 줄씩 대조하기 전에는 「반영 완료」라고 하지 않는다. 과거 작업의 교훈을 이번 작업의 완료 증거로 쓰지 않는다.

## 전달 시 보고 (짧게)

1. 산출물(장별 PNG 또는 요청 형식)
2. 요구사항별 충족 여부(매핑표의 각 행에 ✓)
3. claims 통계(총 / verified / estimate / removed)와 removed로 뺀 내용
4. 렌더 검수에서 고친 장 목록

## ✅ 최종 자기 점검

- [ ] 요구사항→장 매핑표가 있고 모든 행이 채워졌다
- [ ] 모든 헤드라인이 주제명이 아니라 결론 문장이다
- [ ] 각 장의 하단 근거가 헤드라인을 실제로 지지한다
- [ ] 모든 수치·사건·인용이 claims.json에 장 번호와 함께 있다
- [ ] removed claim이 어떤 장에도 남아 있지 않다
- [ ] 산출물에 「미확인」「확인 필요」류 문장이 없다
- [ ] 전 장을 렌더링해 이미지로 확인했다
- [ ] 수정한 오류 유형을 전 장에서 다시 찾았다
- [ ] 고객 템플릿·확정된 장을 요청 없이 바꾸지 않았다
